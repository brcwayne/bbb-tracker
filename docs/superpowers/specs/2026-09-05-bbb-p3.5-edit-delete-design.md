# P3.5 — Edit/Delete of Manual Records + Backdated Entry — Design

## Purpose

P2 shipped create-only manual entry (transactions, cashflows, asset transfers, brokers) plus Drive writes, but explicitly deferred edit/delete and hardcoded every entry's date to "today." Enis asked for both as the direct next phase ("önce sadece ekleme ile başlayalım ama sonra mutlaka diğer özellikleri ekleyelim"). This spec adds: editing and deleting manual records, and a date field on all 4 entry forms so backdated (and only backdated — never future) entries are possible.

## Scope

**In:**
1. Edit and delete for all 4 manual record kinds: Transaction, Cashflow, AssetTransfer (all id-keyed), Broker (kod-keyed, no id field).
2. A date field on all 4 entry forms — defaults to today, editable, rejects any date after today.
3. A list view per record kind, showing only `kaynak: 'manual'` rows, each with Edit / Delete actions.
4. Generalizing `store.ts`'s write path: `appendRecord` stays for create; new `updateRecord`/`deleteRecord` share its Drive conflict-retry mechanics via one common helper.

**Out (deliberately, YAGNI):**
- Editing or deleting migration-sourced (`kaynak: 'migration'`) records — Excel history stays read-only in-app. If Enis ever needs to correct migrated data, that still goes through direct Drive file editing, same as today.
- Soft-delete / audit trail / undo. This is a personal trading journal, not a shared ledger with compliance requirements — a plain confirm-then-remove is enough (Ruling P3.5-1, see below).
- Adding new instruments/brokers/portfolios beyond what P2 already allows (unchanged).
- Bulk edit/delete (multi-select). One record at a time, matching every other interaction in the app so far.

## Global Constraints

(Carried from P1/P1.6/P2, still binding, plus new ones for this phase)

- **Ruling P1-9** (still active): `app/svelte.config.js` is never touched.
- **Ruling P1-10** (still active): components use a `view` prop, never one literally named `derived`.
- All user-facing amounts go through `money()`.
- Financial data (`data/*.json`) never enters the repo or build output; writes go straight from the browser to Drive.
- **Ruling P2-1** (still active): every manual record carries `kaynak: 'manual'`; cash-balance and edit/delete logic both key off this field, never a date cutoff.
- **Ruling P2-2** (still active): `AssetTransfer` records never enter `derive.ts`'s cost/lot math.
- **Ruling P3.5-1 (new, load-bearing):** delete is a hard, permanent removal from the JSON array — no soft-delete flag, no tombstone. Reasoning: `deriveAll` recomputes every derived value fresh from the full dataset on every load/save (no cached per-record state to invalidate), so removing a record from its array is sufficient and correct by construction — there is nothing else to reconcile.
- **Ruling P3.5-2 (new, load-bearing):** only `kaynak === 'manual'` records are editable/deletable, enforced both in the list view (migration rows never render action buttons) and in `updateRecord`/`deleteRecord` (throw if the target record's `kaynak !== 'manual'`, defense in depth against a stale UI state).

## Section 1 — Store: generalizing the write path

Current `appendRecord<T>(store, source, file, record)` in `store.ts` does: read current dataset → build a new array → `source.save()` → on `ConflictError`, reload fresh and retry once → update the store with a fresh `deriveAll`. Edit and delete need the exact same shape, differing only in how the new array is built. Factor that out:

```ts
async function writeAndCommit(
  store: Writable<AppState>,
  source: DataSource,
  file: 'transactions' | 'cashflows' | 'assetTransfers' | 'brokers',
  build: (current: unknown[]) => unknown[],
): Promise<void> {
  if (!source.save) throw new Error("Bu kaynakta kayıt değiştirilemez — sadece Google Drive'a yazılabilir.")
  const state = get(store)
  if (!state.dataset) throw new Error('Veri henüz yüklenmedi.')

  const attempt = async (ds: Dataset): Promise<Dataset> => {
    const updatedArray = build(ds[file] as unknown as unknown[])
    await source.save!(file, updatedArray)
    return { ...ds, [file]: updatedArray }
  }

  let newDataset: Dataset
  try {
    newDataset = await attempt(state.dataset)
  } catch (e) {
    if (!(e instanceof ConflictError)) throw e
    const fresh = await source.load()
    newDataset = await attempt(fresh)
  }

  store.set({ status: 'ready', dataset: newDataset, derived: deriveAll(newDataset), sourceText: state.sourceText })
}

export async function appendRecord<T>(store: Writable<AppState>, source: DataSource, file: Kind, record: T) {
  return writeAndCommit(store, source, file, (current) => [...current, record])
}

export async function updateRecord<T extends { kaynak: string }>(
  store: Writable<AppState>, source: DataSource, file: Kind,
  matches: (r: T) => boolean, patch: T,
) {
  return writeAndCommit(store, source, file, (current) => {
    const arr = current as T[]
    const idx = arr.findIndex(matches)
    if (idx === -1) throw new Error('Kayıt bulunamadı — başka bir yerden silinmiş olabilir.')
    if (arr[idx].kaynak !== 'manual') throw new Error('Sadece manuel kayıtlar düzenlenebilir.')
    const next = [...arr]
    next[idx] = patch
    return next
  })
}

export async function deleteRecord<T extends { kaynak: string }>(
  store: Writable<AppState>, source: DataSource, file: Kind,
  matches: (r: T) => boolean,
) {
  return writeAndCommit(store, source, file, (current) => {
    const arr = current as T[]
    const target = arr.find(matches)
    if (!target) throw new Error('Kayıt bulunamadı — başka bir yerden silinmiş olabilir.')
    if (target.kaynak !== 'manual') throw new Error('Sadece manuel kayıtlar silinebilir.')
    return arr.filter((r) => !matches(r))
  })
}
```

`matches` is a predicate rather than a bare id because `Broker` has no `id` field — its caller passes `(b) => b.kod === targetKod`; the other three kinds pass `(r) => r.id === targetId`. `Kind` is the existing `'transactions' | 'cashflows' | 'assetTransfers' | 'brokers'` union already in `store.ts` (currently inlined on `appendRecord`'s signature — named as a type alias here so all three functions share it).

## Section 2 — Date field on the 4 forms

Each of `IslemFormu.svelte`, `NakitHareketiFormu.svelte`, `VarlikTransferiFormu.svelte`, `KurumFormu.svelte` (Broker has no `tarih` field at all — see 2.1) currently builds its record with a hardcoded `tarih: new Date().toISOString().slice(0, 10)`. Add a `<input type="date">` bound to `let tarih = $state(todayIso())`, wired into the existing review/confirm flow like every other field, with one validation rule added to each form's existing `review()` validator: `if (tarih > todayIso()) errors.push('Tarih gelecekte olamaz.')`. `todayIso()` is a 3-line local helper (`new Date().toISOString().slice(0,10)`) — no new shared module needed, it's already duplicated inline across the 3 forms that need it today.

### 2.1 KurumFormu has no date

`Broker` has no `tarih` field (confirmed: `{kod, ad, tur, sahip, aktif}`). No date input is added to `KurumFormu.svelte` — nothing to backdate.

## Section 3 — List view + Edit/Delete UI

`EkleKaydi.svelte`'s picker gains a second row of buttons alongside the 4 create buttons: "İşlemlerim" / "Nakit Hareketlerim" / "Transferlerim" / "Kurumlarım" — selecting one shows a list of that kind's `kaynak === 'manual'` records (date, one-line summary, Edit/Delete buttons), sourced directly from `dataset.transactions.filter(t => t.kaynak === 'manual')` etc. (no new derived module needed — this is a display-only filter, not a computation).

- **Edit**: clicking Edit on a row sets `kind` to that form's create-kind AND passes an `editing` prop (the full record) into the form. Each form's `$props()` gains an optional `editing?: T`; when present, the form's local state initializes from it (`$state(editing?.field ?? defaultValue)` per field) and the confirm step calls `updateRecord` instead of `appendRecord`, matching on `id` (or `kod` for Broker). The confirm-summary button label changes from "Onayla ve Kaydet" to "Onayla ve Güncelle" when `editing` is set.
- **Delete**: clicking Delete on a row shows an inline two-step confirm (same UX pattern as every form's existing review→confirm step): "Sil" → "Bu işlem geri alınamaz. Emin misiniz? [Evet, sil] [Vazgeç]" → calls `deleteRecord`.
- After a successful edit or delete, the list view refreshes from the (now-updated) `dataset` prop reactively (Svelte's `$derived` over the prop — no manual refetch) and shows the same green `successMessage` pattern already in `EkleKaydi.svelte`.

No new route, no new top-level page — this lives entirely inside the existing "Ekle" tab (nav label unchanged; a page-internal sub-nav is enough and keeps the router untouched, honoring YAGNI over restructuring `router.ts`/`App.svelte` again).

## Section 4 — Edit's effect on downstream calculations

Because `deriveAll` recomputes every derived value (positions, cost basis, realized P&L, attribution, cash balances) fresh from the full dataset arrays on every store update, editing or deleting a `Transaction` automatically and correctly reflows through `derivePositions`'s FIFO lot matching, and editing/deleting an `AssetTransfer` automatically reflows through `attributionEvents`/`latestFieldByKod`. **No incremental invalidation code is needed anywhere** — this was the risk P2's spec flagged for "a future phase" and it resolves for free from the existing architecture (everything is pure functions over the whole dataset, nothing is cached per-record). This is worth stating explicitly so no implementer invents unnecessary invalidation logic.

One real consequence worth surfacing to the user: editing or deleting a `Transaction` that was part of an already-closed position (SAT that closed a lot) can change that position's realized gain/loss figure, retroactively, anywhere it's displayed (Panorama's P&L totals, Pozisyonlar's closed-trades table). This is correct behavior (the user is telling the app "this record was wrong"), not a bug — no special-casing needed, just noted here so it isn't mistaken for one during review.

## Section 5 — Validation rules (new/changed only; P2's existing rules still apply)

- Date field: never after today (Section 2).
- Edit reuses every validation rule the create path already has for that form (lot-availability check, required fields, etc.) — validated against the dataset *excluding* the record being edited (so editing a Transaction's own lot count doesn't self-reject against its own prior value). Concretely: `derivePositions` and the SAT-lot-availability check already operate on `dataset.transactions`; when editing, build the check's input as `dataset.transactions.filter(t => t.id !== editing.id)` before appending the edited draft, exactly mirroring how a plain create appends to the full array.
- Delete has no numeric validation — only the `kaynak === 'manual'` guard (Ruling P3.5-2) and the two-step confirm.

## Section 6 — Test Strategy

Same pattern as P2: `writeAndCommit`/`updateRecord`/`deleteRecord` get unit tests with a mocked `DataSource` (successful update, successful delete, `ConflictError` → reload-and-retry-once, second conflict → surfaces the error, attempt to edit/delete a `kaynak: 'migration'` record → throws). Each form's edit-mode gets a test asserting pre-filled fields from an `editing` prop and that confirm calls `updateRecord` with the right predicate. The list view gets a test asserting migration rows are excluded and Edit/Delete wire to the right callbacks. Date-rejection (future date) gets one test per form, mirroring the existing per-form validation test style.

## Out of Scope — Notes

Bulk operations and soft-delete/undo were considered and explicitly cut (YAGNI) — see Scope. If Enis later needs an audit trail (e.g., because he wants to see what a record looked like before an edit), that would need a real design pass on where history is stored (a new Drive file, most likely) and is not a small addition to this phase.
